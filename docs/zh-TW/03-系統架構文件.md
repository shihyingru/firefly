# 03|系統架構文件

> 螢火 Firefly|v0.1|2026-07-20|AGPL-3.0

## 目標與約束

- 單人維運可承受:初期單一 VPS,全容器化,零維運假期依賴
- AI 成本攤提型:每叢集僅起草一次,查詢吃快取
- 所有元件可被第三方重跑驗證(AGPL-3.0)

## 元件總覽

```
[LINE Bot] [Threads Bot] [分享目標 App] [仲裁佇列] [外掛(後期)]
        \        |          |            /
              [API Gateway]
                   |
     +-------------------------------+
     |         AI 管線(文件04)       |
     | 指紋偵測 → 語意聚類 → 卡片起草 |
     +-------------------------------+
                   |
        [人類仲裁(一鍵投票)]
                   |
```

## 技術選型(建議,可由實作模型調整)

| 層 | 選型 | 理由 |
|---|---|---|
| API 服務 | Python + FastAPI | 與 ML 生態同語言,單人維護成本低 |
| 資料庫 | PostgreSQL + pgvector | 關聯資料與向量檢索同庫,免去獨立向量庫維運 |
| 佇列 | Redis(RQ/Celery) | 指紋偵測與卡片起草皆非同步任務 |
| 快取 | Redis | 卡片查詢命中快取,LINE/Threads 回覆秒回 |
| 嵌入模型 | 多語 embedding(可自架 small model) | 聚類成本趨近零 |
| 起草 LLM | 外部 API,每叢集一次 | 攤提成本;prompt 與輸出全記錄於審計 log |
| 部署 | Docker Compose → 單 VPS;之後 k8s 可選 | 初期簡單優先 |
| 監控 | 開源方案(如 Grafana/Prometheus) | 儀表板數據同時供內部監控與公開透明層 |

## 資料流(查詢路徑)

1. 入口收到連結 → Gateway 正規化 URL → 查快取
2. 命中:直接回卡(p50 < 1s)
3. 未命中:建立貼文快照任務 → 指紋偵測 → 聚類歸屬 → 若叢集無卡則觸發起草 → 回卡並快取

## 資料流(仲裁路徑)

1. 投票經 Gateway 寫入投票庫(附匿名貢獻者代號)
2. 橋接引擎批次重算(初期每小時;規模化後增量計算)
3. 卡片顯示狀態更新:候選 → 顯示 / 退回

## 關鍵取捨紀錄(ADR 摘要)

- **單庫 pgvector vs 專用向量庫**:選前者。量級(十萬~百萬則)內效能足夠,少一個維運面
- **批次重算 vs 即時計分**:選批次。橋接演算法需全域矩陣分解,即時化複雜度不值得
- **自架 LLM vs API**:選 API。每叢集一次的用量撐不起自架;透明性以記錄 prompt/輸出達成
- **Stage 3 確定性優先(2026-09-03)**:白名單欄位由程式計算,LLM 僅對 original_source 提候選且限於封閉集合,預設關閉。理由:縮小注入與幻覺面;卡片可 100% 由資料重放
- **平台依賴風險**:Threads/LINE 均可能斷供;分享目標 App 為全自主保底入口,故列第二波必做

## 擴張路徑

- 多語言:embedding 模型本身多語;指紋規則按語言分包
- 多平台:偵測層新增來源 adapter(Facebook/YouTube 留言等),下游不變
- 跨國部署:整套 Docker 化,他國社群可自行架設(AGPL 保證衍生服務開源)
